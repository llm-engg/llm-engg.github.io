Recap: Inference Optimization Techniques

  • Continuous Batching

  • Dynamically batch requests at the token level, allowing for early return and better GPU utilization.

  • As soon as one request in the batch finishes generating its next token, it can be returned to the client, while the remaining requests continue processing.

Recap: Inference Optimization Techniques

  • Paged Attention

  • Each request’s KV cache is divided into multiple physical blocks (pages) that can be allocated independently.

  • Multiple requests can share the same physical blocks if they have similar context lengths, improving memory efficiency and GPU utilization.

LLM Inference Patterns

Prefix sharing patterns:

  1. System Prompts: All users share the same 1K-4K token system instructions
  2. RAG Context: Multiple queries against the same document chunks
  3. Multi-turn Conversations: Every request includes the same system prompt (“You are a helpful assistant…”).
  4. Agent Workflows: ReAct patterns with repetitive tool descriptions

Prefix Caching

  • Reusable KV cache
  • Only depends on the prefix tokens

Example:
System Prompt: 2,000 tokens
User Query: 50 tokens
Response: 500 tokens

Without caching: Process 2,050 tokens every request.
With caching: Process 50 tokens (user query only) -> 97% reduction!

Prefix Caching

Measured improvements:

  • TTFT (Time to First Token) reduction: 5-20× faster for cache hits

  • GPU compute saved: 40-90% for workloads with shared prefixes

  • Memory overhead: near-zero with PagedAttention (shared physical blocks)

Economic Impact:

  • At 1M requests/day with 2K shared prefix

  • Savings: 2B tokens of redundant compute daily

  • Cost reduction: $10K-50K/day depending on model size

Prefix caching can reduce compute and latency by an order of magnitude in some use cases.

Prefix Caching

  • Anthropic Claude Sonnet, Google Gemini -> Up to 90% cost savings and 85% latency reduction with prompt caching.
  • Frameworks like vLLM, TensorRT-LLM, and SGLang support automatic prefix caching for different open-source LLMs.
  • In agent workflows, the benefit is even more pronounced (input-to-output token ratios of 100:1)

vLLM Prefix Caching

vLLM implements hash-based automatic prefix caching (enabled with --enable-prefix-caching by default):

  • Each KV block is hashed based on its token content
  • If a hash matches an existing block in the cache -> reuse it (skip prefill for those tokens)
  • LRU eviction, Block-level granularity

Can we do this at token level?

RadixAttention (SGLang)

Paper: SGLang: Efficient Execution of Structured Language Model Programs - Zheng et al., NeurIPS 2024

RadixAttention, which uses a radix tree data structure for KV cache management:

(root)
 ├── "cat"
 │     ├── "sat"   (cat sat)
 │     └── "flew"   (cat flew)
 └── "dog"
  • All seen token sequences are stored in a radix tree
  • Each node in the tree points to cached KV blocks in GPU memory

RadixAttention (SGLang)

green - newly added nodes | blue - cached nodes accessed during the time point | red - nodes that have been evicted

  • Edges are labeled with token sequences (not single tokens, space-efficient)
  • New request: traverse the tree to find the longest matching prefix
  • Only compute KV for the remaining (unmatched) tokens

RadixAttention (SGLang)

  • RadixAttention enables efficient prefix matching, insertion, and eviction.
  • It handles trees with hundreds of thousands of tokens.

Radix Attention

  • LRU eviction when memory pressure occurs

Cache Aware Scheduling

  • Sort waiting requests by matched prefix length - schedule longer matches first to maximize cache hits

When Caching Doesn’t Help

  1. Unique contexts: Zero shot tasks with no shared prompts
  2. Very long sequences: When KV cache size >> compute cost
  3. High churn: Cache eviction rate > hit rate
  4. Short prefixes: Overhead dominates for < 100 token prefixes

The Hardware Mismatch Problem

Modern GPUs are designed for training (compute-bound), but inference has asymmetric needs:

Prefill Requirements:

  • High FLOPS (tensor cores)
  • Moderate memory bandwidth

Decode Requirements:

  • High memory bandwidth (HBM)
  • Large memory capacity (for KV cache)
  • Lower compute acceptable

The Problem: Single GPU must satisfy both, leading to over-provisioning.

Phase Colocation Issues

When prefill and decode share GPUs:

Batching Tradeoffs:

  • Mixing phases causes interference
  • Batching prefills helps utilization but increases TTFT
  • Batching decodes helps throughput but increases TPOT

SLO Conflicts:

  • TTFT (Time To First Token) requires fast prefill
  • TPOT (Time Per Output Token) requires uninterrupted decode
  • Optimizing one hurts the other

Continuous Batching Batch R1 and R2 together in 1 GPU

Separate prefill / decode R1 and R2 in separate GPUs

Resource Contention:

  • Prefill saturates compute -> decode stalls
  • Decode saturates bandwidth -> prefill slows

Overprovision Resource to meet SLO

When Does Disaggregation NOT Make Sense?

  • Low request volume: Not enough requests to justify separate pools
  • Very short prompts: Prefill is already cheap, transfer overhead dominates
  • Single GPU deployments: No other GPUs to disaggregate onto
  • Low-latency requirements: KV cache transfer adds latency that may violate tight SLOs

Choosing Your Stack: Scenario-Based

Scenario 1:

“Run a chatbot on my desktop / laptop” -> llama.cpp with Q4_K_M quantization, Metal backend. Full privacy, no cloud needed.

Scenario 2:

“Serve Llama-70B to 100 concurrent users on 4× A100” -> vLLM or SGLang with tensor parallelism. Enable prefix caching for chat workloads.

Scenario 3:

“Structured JSON extraction from documents at scale” -> SGLang — RadixAttention maximizes prefix reuse for repeated templates, compressed FSM for structured output.

Scenario 4:

“Deploy DeepSeek-R1 across a 64-GPU cluster” -> NVIDIA Dynamo with disaggregated serving, vLLM or TRT-LLM backend. Smart router for KV cache locality.

Key Takeaways

  1. Prefill is compute-bound, decode is memory-bound
  2. Continuous batching (Orca) eliminates idle GPU time by scheduling at iteration level -> 2-36× throughput over static batching
  3. PagedAttention (vLLM) eliminates KV cache fragmentation with OS-inspired virtual memory -> reduces waste from 60-80% to <4%, enabling 2-4× more throughput
  4. Prefix caching avoids redundant prefill computation -> 5-20× TTFT reduction for workloads with shared prefixes
  5. Disaggregated serving (DistServe) separates prefill and decode onto different GPUs -> independent optimization and 1.4-2.35× throughput improvement
  6. Production orchestration (NVIDIA Dynamo) adds smart routing, dynamic scaling, KV cache management, and SLO-aware planning across GPU clusters -> up to 7× throughput on Blackwell
