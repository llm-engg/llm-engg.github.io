LLM Inference Challenges

Why is LLM inference harder than standard neural network inference?

  • Variable-length compute : inputs and outputs have no fixed tensor shapes
  • Batching is difficult : sequences finish at different times
  • Need to balance TTFT, ITL, and throughput simultaneously

LLM Inference Challenges

Why is LLM inference harder than standard neural network inference?

  • Two distinct phases: prefill (compute-intensive) vs decode (memory-intensive)
  • Two different compute characteristics -> need different optimizations

Arithmetic Intensity

\[\text{Arithmetic Intensity} = \frac{\text{Compute FLOPs}}{\text{Memory Bytes}}\]

AI tells you whether the model is spending time computing (doing math) or fetching (moving data).

  • Low AI = GPU mostly waiting for data.
  • High AI = GPU mostly doing useful computation.

Prefill vs Decode

Property Prefill Phase Decode Phase
Operation type GEMM (matrix × matrix) GEMV (matrix × vector)
Arithmetic intensity High Very low
GPU utilization High (saturates compute) Low (limited by bandwidth)
Bottleneck Compute (FLOPS) Memory bandwidth (GB/s)
Parallelism All prompt tokens in parallel One token at a time, sequential
Time scaling ∝ prompt_length ∝ output_length × kv_cache_size
Batch dimension batch_size × seq_len (large) batch_size × 1 (small)

The Roofline Model

Performance is bounded by:

  1. Compute : how fast GPU does math (FLOPs/s)
  2. Bandwidth : how fast data moves (GB/s)
  3. Capacity : whether weights + KV cache fit at all (GB)

Note

Knee point = bandwidth-bound to compute-bound transisiton -> minimum AI needed to fully utilize GPU’s compute.

Inference Tradeoffs

Three way tradeoff between accuracy, latency, and cost

Cannot optimize for all three simultaneously.

Priority Tradeoff Engineering Bridges
Accuracy + Low Latency Higher cost Use smaller models to reduce serving cost; recover accuracy with RAG, fine-tuning, and tool use. Quantization cuts GPU memory footprint further.
Accuracy + Low Cost Higher latency Batch inference, async pipelines, and queue-tolerant architectures absorb the latency gracefully.
Low Latency + Low Cost Accuracy at risk Smaller or distilled models with quantization; improve accuracy via RAG, fine-tuning

Static Batching / Request-Level Batching

Traditional systems use static batching to improve GPU utilization:

  • Group incoming requests into fixed-size batches (e.g., 8, 16, 32)
  • Process each batch in parallel on the GPU
  • High GPU utilization for large batches

Drawbacks:

  • No early return and tail latency dictated by longest sequence in the batch
  • Internal fragmentation from padding to max sequence length
  • GPU utilization: 30-40% for small batches, drops to 10-20% for larger batches due to padding overhead

Continuos Batching

Orca : A Distributed Serving System for Transformer-Based Generative Models, 2022

  • Do dynamic batching of requests as they arrive
  • Process batchig at token level instead of request level
  • Early return as soon as a request in the batch finishes
  • Support for token-level interleaving of requests

Continuous Batching

Continuous Batching

Continuous Batching:

  • Dynamically batch requests at the token level, allowing for early return and better GPU utilization.
  • As soon as one request in the batch finishes generating its next token, it can be returned to the client, while the remaining requests continue processing.

Early finished and late arrived requests are handled much more efficiently. The server can immediately return results for completed requests without waiting for the entire batch to finish, significantly reducing tail latency and improving user experience.

Prefill and Decode in continuos batching

  • Some requests can be in prefill phase while others are in decode phase
  • We can’t batch prefill and decode together since they have different compute and memory characteristics

Continuous Batching Mechanics

The Loop:

  1. Selection: Choose candidate requests for next iteration
  2. Batch Formation: Combine prefill chunks and decode tokens
  3. Forward Pass: Run model on current batch
  4. Completion Check: Identify finished sequences
  5. Admission: Add new requests from queue
  6. Iteration: Repeat

Benefits:

  • No Waiting: Short requests exit immediately, don’t wait for long ones
  • GPU Saturation: Keep compute units busy 80%+ of time

Chunked Prefill

A large prefill can dominate an iteration and spike latency for decode requests.

Chunked prefill addresses this:

  • Split large prefills into chunks (e.g., 512 tokens at a time)
  • Interleave prefill chunks with decode steps
  • Prevents a single large prefill from blocking decode for all other requests

This is now standard in vLLM (enabled by default) and SGLang.

Scheduling Policies

Scheduling

  • First-Come-First-Served (FCFS)

  • Priority-Based

  • Longest Prefix Match (LPM)

Preemption Strategies:

  1. Swap: Move KV cache to CPU memory when preempting

  2. Recompute: Discard KV cache, regenerate when resuming

    • Cost: 2× compute for the prompt
    • Benefit: No memory bandwidth cost for swap

Rule of Thumb: Swap for long sequences (KV cache >> compute cost), recompute for short sequences.
