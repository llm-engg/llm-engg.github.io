    Lecture Prep Notes: Memory Systems and Multi-Agent Systems

    3. Multi-Agent Systems

    3.1 Why Multi-Agent Systems Exist

    A multi-agent system uses multiple model contexts or agents that coordinate to solve a task.

    Three real reasons multi-agent can help:

    1. Specialization
    2. Parallelism
    3. Adversarial or review dynamics

    Add a fourth practical reason:

    1. Context isolation

    Specialization:

    Different agents get different prompts, tools, permissions, or models.

    Examples:

    • Researcher searches sources.
    • Coder edits files.
    • Reviewer critiques diff.
    • Test-runner executes tests.
    • Security reviewer checks risky changes.

    Parallelism:

    Independent subtasks run at the same time.

    Examples:

    • Search frontend and backend in parallel.
    • Generate multiple candidate solutions.
    • Run independent benchmark shards.
    • Have multiple workers attempt separate bugs.

    Adversarial dynamics:

    Agents improve output by challenging each other.

    Examples:

    • Solver and critic.
    • Solver, adversary, judge.
    • Debate between candidate answers.
    • Red-team agent attacks a plan.

    Context isolation:

    Each worker gets a fresh, focused context. Search noise, failed attempts, and long tool outputs do not pollute the orchestrator's context.

    Teaching phrase:

    "Often the win is not that the agents are smarter as a team. It is that each one is less distracted."

    3.2 When Single-Agent Is Better

    Start with single-agent unless there is a clear reason not to.

    Single-agent is usually better when:

    • The task is linear.
    • One toolset is enough.
    • Debuggability matters.
    • Cost matters.
    • Low latency matters.
    • The task needs one coherent global judgment.

    Multi-agent adds:

    • More prompts
    • More LLM calls
    • More handoff failures
    • More state-management problems
    • More places to hide bugs
    • More latency
    • More evaluation complexity

    Important reliability calculation:

    If each stage is 90% reliable and five stages must all succeed, total reliability is:

    0.9^5 = 0.59049

    So a chain of individually good agents can still be unreliable.

    Use this to make students skeptical of agent teams.

    3.3 Multi-Agent Architecture Patterns

    Pattern 1: Supervisor and Workers

    Shape:

    User -> Supervisor -> Worker A
                  -> Worker B
                  -> Worker C
       Supervisor aggregates final answer

    Use when:

    • Task requires dynamic routing.
    • Supervisor needs global state.
    • Workers have distinct skills/tools.

    Pros:

    • Flexible
    • Easy mental model
    • Good for coding-agent orchestration

    Cons:

    • Supervisor becomes bottleneck.
    • Supervisor context can rot.
    • Bad delegation ruins worker performance.

    Coding-agent example:

    • Orchestrator decomposes task.
    • Explorer investigates codebase.
    • Implementer edits.
    • Reviewer inspects diff.
    • Test-runner runs commands and summarizes failures.

    Pattern 2: Sequential Pipeline

    Shape:

    Planner -> Architect -> Implementer -> Reviewer -> Tester

    Use when:

    • Workflow is well-known.
    • Each phase has clear input/output.
    • You want predictability.

    Pros:

    • Simple
    • Easy to evaluate each stage
    • Good for production workflows

    Cons:

    • Rigid
    • Early errors propagate
    • Feedback loops must be added explicitly

    Example:

    MetaGPT-style software company simulation: product manager writes requirements, architect designs, engineer implements, QA reviews.

    Pattern 3: Graph with Conditional Edges

    Shape:

    Planner -> Coder -> Reviewer
              ^        |
              |        v
          needs changes?

    Use when:

    • Work needs cycles.
    • Reviewer can send task back.
    • State transitions must be explicit.

    Pros:

    • More controllable
    • Debuggable
    • Good fit for LangGraph-style systems

    Cons:

    • Requires upfront graph design.
    • Too much structure can be brittle.

    Pattern 4: Debate or Adversarial System

    Shape:

    Solver A -> argues answer
Solver B -> critiques or proposes alternative
Judge -> selects or synthesizes

    Use when:

    • Reasoning quality matters.
    • There are multiple plausible answers.
    • Critique is cheap relative to failure.

    Pros:

    • Can catch reasoning errors.
    • Useful for factuality and math reasoning.
    • Natural fit with LLM-as-judge eval.

    Cons:

    • Can amplify confident nonsense.
    • Judge can be biased.
    • Expensive if many debate rounds.

    Class lab:

    Implement solver-adversary-judge on math reasoning and compare against a single-agent baseline with equal total compute.

    Pattern 5: Parallel Fleet

    Shape:

    Planner -> Worker 1
        -> Worker 2
        -> Worker 3
Aggregator -> merge results

    Use when:

    • Subtasks are independent.
    • Latency matters.
    • You can isolate workspaces.

    Examples:

    • Run three codebase explorers on different modules.
    • Generate multiple candidate fixes in separate git worktrees.
    • Search several data sources at once.

    Pros:

    • Faster wall-clock time.
    • Diverse solutions.
    • Good use of independent context windows.

    Cons:

    • Merge conflicts.
    • Duplicate work.
    • Aggregator must judge quality.
    • More infrastructure.

    Pattern 6: Classifier-Based Routing

    Shape:

    Input -> classifier/router -> selected specialist

    Use when:

    • Routing categories are stable.
    • You want lower latency and cost than LLM supervisor routing.
    • You have good descriptions or training examples.

    Pros:

    • Fast
    • More deterministic
    • Less supervisor context rot

    Cons:

    • Less flexible
    • Needs maintenance as specialists change

    3.4 Communication Between Agents

    Agents can communicate through:

    • Natural language messages
    • Structured JSON
    • Shared state objects
    • Typed artifacts
    • Shared blackboard or memory stream
    • Files
    • Tool calls
    • Protocols such as MCP or A2A-style handoffs

    Important distinction:

    Communication format determines failure modes.

    Natural language:

    • Flexible
    • Easy for LLMs
    • Ambiguous
    • Hard to validate

    Structured messages:

    • Easier to validate
    • Better for production
    • More schema design work
    • Can be too rigid

    Shared state:

    • Good for graph workflows
    • Easy to checkpoint
    • Risk of agents overwriting each other

    Artifact passing:

    • Good for pipelines
    • Each stage produces a typed output
    • Clear interface between roles

    For coding agents, prefer concise handoff artifacts:

    Explorer output should include:

    • Files inspected
    • Relevant findings
    • Exact locations
    • Uncertainties
    • Suggested next files

    Implementer output should include:

    • Files changed
    • Summary of behavior change
    • Tests run
    • Remaining risk

    Reviewer output should include:

    • Blocking issues
    • Non-blocking suggestions
    • Test gaps
    • Approval or requested changes

    Bad handoff:

    I looked around and auth is complicated. You should probably check the token code.

    Good handoff:

    Relevant files:
- `src/auth/jwks.py`: fetches and caches signing keys.
- `src/auth/middleware.py`: validates bearer tokens.
- `tests/test_auth.py`: failing test uses expired fixture token.

Finding:
The route failure is likely not middleware registration. The request reaches `validate_token`, then fails on JWKS cache lookup.

Uncertainty:
I did not inspect production config loading.

    3.5 Role Design

    A role prompt is a specification, not a costume.

    Weak role:

    "You are a brilliant senior engineer."

    Better role:

    "You are the codebase explorer. Your job is to answer where relevant code lives and how it works. You may read files and search text. Do not edit files. Return concise findings with file paths and line references. Do not include full file contents."

    Role design should define:

    • Goal
    • Allowed tools
    • Forbidden actions
    • Input contract
    • Output contract
    • Stop condition
    • Quality bar
    • Escalation conditions

    Good specialist roles have narrow toolsets.

    Example:

    • Explorer: rg, read_file, list_dir
    • Implementer: read_file, edit_file, maybe no test execution
    • Test-runner: run_tests, read_logs, no editing
    • Reviewer: git_diff, read_file, no editing

    Why narrow tools help:

    • Smaller prompt
    • Less tool-selection confusion
    • Reduced blast radius
    • Easier eval
    • Better security boundary

    3.6 Context Isolation

    This is the most important practical multi-agent idea.

    Single-agent problem:

    The main agent explores many files, runs commands, sees errors, reads irrelevant docs, changes plan, and carries all of that noise forward. As the context grows, irrelevant but semantically related facts become distractors.

    Multi-agent solution:

    Delegate noisy phases to fresh contexts. The worker does messy exploration and returns only a compact summary.

    Example:

    def explore_codebase(question):
    worker = Agent(
        role="code explorer",
        tools=[rg, read_file],
        instruction="Return only relevant files, findings, and uncertainties."
    )
    return worker.run(question)

    The orchestrator should not receive:

    • Every file read
    • Every failed search query
    • Full stack traces unless needed
    • The worker's hidden reasoning

    The orchestrator should receive:

    • Answer
    • Evidence
    • Confidence
    • Next recommended action
    • Uncertainties

    Important nuance:

    Context isolation fails if the worker returns a verbose transcript. Then you paid for another agent without reducing context pollution.

    3.7 Multi-Agent Failure Modes

    Coordination Overhead

    Agents spend more effort explaining work to each other than doing the work.

    Symptoms:

    • Long handoffs
    • Repeated clarifying messages
    • Supervisor keeps re-planning
    • Workers duplicate each other

    Mitigation:

    • Clear input/output contracts
    • Fewer agents
    • Shared task state
    • Typed artifacts

    Error Propagation

    One worker produces a wrong summary; downstream agents trust it.

    Mitigation:

    • Include evidence in handoffs.
    • Reviewer checks critical claims.
    • Require file paths, commands, or citations.
    • Let downstream agents challenge upstream assumptions.

    Context Fragmentation

    No agent has enough global context to make the right decision.

    Mitigation:

    • Supervisor keeps a compact global state.
    • Workers receive sufficient task background.
    • Critical constraints are repeated in every worker prompt.

    Role Confusion

    Workers perform actions outside their responsibility.

    Mitigation:

    • Narrow tools.
    • Explicit forbidden actions.
    • Validate output.
    • Use separate permissions.

    Premature Delegation

    The orchestrator delegates before understanding the task.

    Mitigation:

    • Require the orchestrator to identify dependencies first.
    • Delegate only independent or bounded work.
    • Keep blocking work local when needed.

    Merge Conflicts and State Conflicts

    Parallel implementers edit overlapping files.

    Mitigation:

    • Assign disjoint ownership.
    • Use separate worktrees.
    • Integrate intentionally.
    • Have one final reviewer.

    Judge Failure

    In debate systems, the judge picks the most persuasive answer rather than the correct one.

    Mitigation:

    • Use deterministic verification where possible.
    • Calibrate judge.
    • Require structured rubrics.
    • Use hidden reference tests or execution for code/math.

    3.8 Multi-Agent Evaluation

    Never compare multi-agent to single-agent with unlimited extra compute. That only proves spending more tokens can help.

    Fair comparison:

    • Same task set
    • Same total token or dollar budget
    • Same model family or documented model differences
    • Same time budget if latency matters
    • Same tool access unless testing tool specialization

    Metrics:

    • Task success rate
    • Cost per success
    • Tokens per success
    • Wall-clock time
    • Number of tool calls
    • Number of handoffs
    • Handoff error rate
    • Duplicate work
    • Reviewer catch rate
    • Regression rate

    Questions for analysis:

    • Did multi-agent help through specialization?
    • Did it help through parallelism?
    • Did it help through adversarial critique?
    • Did it help through context isolation?
    • Or did it only use more tokens?

    Coding-agent eval:

    Compare Class 6 single-agent-with-memory against Class 7 orchestrator plus specialists on the same feature task.

    Hypothesis to test:

    The main benefit will be context isolation, not role names.

    4. Connecting Memory and Multi-Agent Systems

    Memory and multi-agent orchestration interact.

    Questions:

    • Does every agent share the same memory?
    • Does each worker have private memory?
    • Can workers write long-term memory?
    • Does the supervisor approve memory writes?
    • Are memories scoped by role?

    Recommended architecture for students:

    • Supervisor owns global task state.
    • Workers get read-only relevant memory.
    • Workers can propose memory writes.
    • Supervisor or reflection step commits memory.
    • Procedural memories require successful verification before promotion.

    Why:

    If every worker can write persistent memory freely, the system accumulates unreviewed, inconsistent beliefs.

    Memory scopes:

    • User memory: stable preferences and user facts.
    • Project memory: architecture, conventions, commands.
    • Task memory: current plan and transient findings.
    • Worker memory: local scratchpad, discarded after task.
    • Procedural memory: skills/playbooks, reviewed or success-gated.

    5. Case Studies to Discuss

    Hermes Agent

    Use for memory discussion.

    Interesting design:

    • Stores cross-session history.
    • Uses SQLite/FTS-style retrieval and summarization.
    • Exposes memory as on-demand recall rather than injecting everything.
    • Learns reusable skills from successful tasks.

    Teaching angle:

    Hermes treats memory as something the agent can query and build on. It is closer to an engineered long-term workspace than to a chatbot transcript.

    Critical question:

    Should an agent be allowed to write its own skills? If yes, what verification threshold is required?

    OpenClaw

    Use for memory plus multi-channel/multi-agent discussion.

    Interesting design:

    • Filesystem-native memory.
    • Prompt files such as agent instructions and skill files.
    • Scheduled/proactive behavior.
    • Delegates coding work to external coding agents.

    Teaching angle:

    OpenClaw shows that "multi-agent" may look like an orchestrator calling another agent process, not a fancy in-process debate framework.

    Critical question:

    Is shelling out to Codex or Claude Code a multi-agent architecture? The practical answer may matter more than the label: there is delegation, context isolation, separate tool policy, and separate execution state.

    Claude Code

    Use as production reference.

    Interesting design:

    • Strong tool loop.
    • Project instruction files.
    • Subagent/task delegation patterns.
    • Human-in-the-loop safety.

    Teaching angle:

    Students should compare their coding-agent spine against a production-grade coding agent: what did they implement, what did they skip, and which skipped pieces are essential?

    Pi

    Use as counterpoint.

    Interesting design:

    • Minimal structure.
    • Code-first self-extension philosophy.
    • Skepticism toward plugin-heavy infrastructure.

    Teaching angle:

    Pi is useful because it challenges the assumption that more architecture is better.

    Critical question:

    When is it cleaner to ask the agent to write code than to build a plugin/skill/multi-agent layer?

    6. Suggested Demos

    Goal:

    Show that memory is useful only when retrieval is precise.

    Setup:

    • Create five memory entries.
    • Three are relevant to a task.
    • One is stale.
    • One is semantically similar but wrong.

    Run:

    • Ask the agent to solve the task with all five injected.
    • Ask again with only top relevant memories.
    • Ask again with no memory.

    • Did memory reduce work?
    • Did bad memory mislead?
    • How should the memory system rank or filter?

    8. Discussion Questions

    Memory:

    • What is the smallest memory system that would improve your coding agent?
    • Which facts should be global user memory versus project memory?
    • Should memory writes require user approval?
    • What should happen when memory conflicts with current repo evidence?
    • Is vector search enough, or do we need structured metadata?

    Multi-agent:

    • When is a second agent better than a second tool call?
    • Is role specialization real, or mostly prompt theater?
    • What should a worker return to an orchestrator?
    • How would you detect duplicate work across workers?
    • Should a reviewer agent have edit permission?

    Through-line:

    • Did adding memory impose useful structure or create stale constraints?
    • Did adding multiple agents impose useful structure or create coordination overhead?
    • What empirical result would convince you to remove the extra structure?

    9. Lab Framing

    Memory Lab

    Build an agent with persistent memory across sessions.

    Required components:

    • SQLite or file store for structured memories.
    • Optional vector store for semantic retrieval.
    • Reflection step at session end.
    • Retrieval step at session start.
    • Memory budget in the prompt.

    Task:

    • Session 1: agent learns project conventions while solving a task.
    • Session 2: new task depends on those conventions.

    Compare:

    • No-memory baseline
    • Memory-enabled agent

    Report:

    • Success rate
    • Steps
    • Tokens
    • Retrieved memories
    • Incorrect memories
    • Whether memory actually changed behavior

    Build a solver-adversary-judge system or coding-agent orchestrator.

    Option A: reasoning benchmark

    • Single solver baseline.

    • Same total compute budget.

    Option B: coding-agent spine

    • Orchestrator
    • Explorer
    • Implementer
    • Reviewer
    • Test-runner

    Compare:

    • Single-agent Class 6 system
    • Multi-agent Class 7 system

    • Did multi-agent help?

    • What failed?
    • What would you remove?

    10. Closing Synthesis

    End with these claims:

    1. Memory is not storage. Memory is storage plus retrieval plus update plus forgetting.
    2. Multi-agent is not magic teamwork. It is context partitioning plus communication overhead.
    3. The best agent systems often look boring: small prompts, narrow tools, explicit state, clear handoffs, measured evals.
    4. Add structure only when it solves a measured problem: repeated rediscovery, stale context, tool overload, lack of verification, or parallelizable work.
    5. The right question is always empirical: did this structure improve success per dollar, success per minute, or reliability?

    Final prompt for students:

    "For your own coding agent, identify one place where memory should help and one place where a subagent should help. Then design the eval that could prove you wrong."

    11. May 2026 Literature and Web Update

    Use this section to update the lecture for the current state of the field as of May 2026.

    The short version:

    • Memory has moved from "vector DB attached to a chatbot" toward managed memory layers, temporal knowledge graphs, explicit memory blocks, and agent-controlled memory tools.
    • Multi-agent systems have moved from demo-heavy group chats toward narrow, production patterns: orchestrator-worker systems, read-only subagents, handoffs, concurrent workers, and explicit workflow graphs.
    • Enterprise deployments now emphasize identity, access control, audit logs, tracing, tool guardrails, data residency, and protocol boundaries as much as prompts.
    • The most useful teaching stance is no longer "single-agent or multi-agent?" It is "which context should hold which information, which actor is allowed to act, and what evidence proves the architecture improves reliability per cost?"

    11.1 Literature Map for Memory

    MemGPT / Letta: Memory as Virtual Context Management

    Core idea:

    MemGPT framed LLM memory as an operating-system-like problem: the model has limited fast memory, so the agent needs mechanisms for moving information between context and external storage.

    Teaching use:

    • Use MemGPT to introduce memory hierarchy.
    • Then show Letta as the production evolution: core memory blocks plus archival memory.

    Implementation details to teach:

    • Core memory blocks are always visible in the agent context.
    • Archival memory is searched on demand.
    • Memory tools let the agent insert, replace, or rethink memory.
    • Developers can programmatically manage memory through SDKs.

    Important production distinction:

    • Always-visible memory should be small, stable, and high-value.
    • Archival memory should hold larger, less frequently needed facts, documents, and historical details.

    Enterprise analogy:

    • Core memory is like the employee's current role brief and active project brief.
    • Archival memory is like a searchable enterprise knowledge base.

    Source notes:

    • MemGPT paper: "MemGPT: Towards LLMs as Operating Systems" (2023).
    • Letta docs describe memory blocks as persistent context sections and archival memory as semantically searchable long-term storage queried by tools.

    Generative Agents: Memory Stream, Importance, Reflection

    Core idea:

    Generative Agents used a memory stream where experiences are stored, scored, retrieved, and periodically reflected on to produce higher-level beliefs.

    Teaching use:

    • Use this paper to explain why raw events are not enough.
    • The key lesson is consolidation: many small observations become fewer higher-level memories.

    Implementation details to teach:

    • Store observations with timestamps.
    • Score relevance, recency, and importance.
    • Retrieve memories by a combined score, not semantic similarity alone.
    • Use reflection to synthesize recurring patterns.

    Enterprise adaptation:

    • For support agents, raw tickets become account-level patterns.
    • For sales agents, raw conversations become customer preferences and buying signals.
    • For coding agents, raw traces become project conventions and known failure modes.

    Risk:

    Reflection can invent patterns that are not true. In enterprise systems, reflection output should carry provenance and confidence.

    Zep: Temporal Knowledge Graphs

    Core idea:

    Zep models memory as a temporal knowledge graph. It stores entities, facts, relationships, and validity intervals, including when facts become invalid.

    Teaching use:

    • Use Zep to explain why enterprise memory is often not just "retrieve similar chunks."
    • Enterprise facts change: a customer changes plan, an owner changes, a policy expires, a project migrates.

    Implementation details to teach:

    • Nodes represent entities.
    • Edges represent facts and relationships.
    • Facts can become invalid without being erased.
    • Retrieval returns a memory context string optimized for the current task.
    • User graphs and group graphs allow user-specific and shared memory.

    Enterprise adaptation:

    • Customer support: "Customer is on Enterprise plan" should have a validity period.
    • HR: "Employee reports to X" changes over time.
    • Finance: "Account owner" and "risk status" must be current and auditable.
    • Coding: "This repo uses Flask" may become invalid after a migration to FastAPI.

    Key lesson:

    Temporal memory is a better fit than plain vector search when correctness depends on what was true at a specific time.

    Mem0: Managed Memory Layer and Graph-Based Memory

    Core idea:

    Mem0 positions memory as reusable infrastructure for agents and apps: add interactions, extract memories, retrieve relevant memory later, and manage governance centrally.

    Teaching use:

    • Use Mem0 to show the "memory-as-a-service" product direction.
    • Useful for explaining build-vs-buy tradeoffs.

    Implementation details to teach:

    • SDK call to add user/assistant messages.
    • Search with filters such as user_id.
    • Managed vector store, graph services, rerankers, governance, and audit logs.
    • Open-source/self-hosted options for data-control requirements.

    Enterprise adaptation:

    • Good fit when many agents need shared user or account continuity.
    • Good fit when teams do not want to build memory extraction, deduplication, and retrieval from scratch.
    • Be careful with regulated data: memory ingestion policy matters more than SDK convenience.

    LangGraph Memory and Persistence

    Core idea:

    LangGraph separates short-term thread state from long-term memory stores and supports checkpointing at each graph step.

    Teaching use:

    • Use LangGraph for the enterprise engineering story: persistence, resumability, human-in-the-loop, and time-travel debugging.

    Implementation details to teach:

    • Short-term memory lives in graph state or thread checkpoints.
    • Long-term memory stores user-specific or application-level data across sessions.
    • Checkpointers save state snapshots at each step.
    • Semantic search can be added to long-term stores.

    Enterprise adaptation:

    • Long-running agents need resumability after failures.
    • Human approval workflows need checkpointed state.
    • Production incidents require traceable step-level state, not only final outputs.

    11.2 Literature Map for Multi-Agent Systems

    AutoGen: Conversable Multi-Agent Frameworks

    Core idea:

    AutoGen made "agents talking to agents" a mainstream abstraction: agents can be customizable, conversable, tool-using, and human-in-the-loop.

    Teaching use:

    • Use AutoGen as the canonical group-chat framing.
    • Then critique where unconstrained group chat fails.

    Implementation lesson:

    Conversable agents are flexible, but flexibility creates coordination and termination problems. Enterprise systems usually need stricter orchestration than open-ended group chat.

    MetaGPT: SOPs and Artifact Pipelines

    Core idea:

    MetaGPT applies standard operating procedures to multi-agent software development. Agents play roles such as product manager, architect, engineer, and QA, passing structured artifacts.

    Teaching use:

    • Use MetaGPT to show the "impose more structure" end of the spectrum.
    • It is a good example of reducing hallucination by forcing intermediate artifacts.

    Implementation lesson:

    For enterprise workflows with known process stages, pipeline plus typed artifacts often beats free-form collaboration.

    Examples:

    • Compliance review pipeline
    • Loan underwriting pipeline
    • Incident response pipeline
    • Software change pipeline

    Multiagent Debate and ChatEval

    Core idea:

    Multiple model instances can propose, critique, and judge answers. Debate can improve reasoning and factuality in some settings, and multi-agent evaluators can align better with human evaluation in some tasks.

    Teaching use:

    • Use debate to teach adversarial dynamics.
    • Then emphasize that debate is not verification.

    Implementation lesson:

    Debate is useful when:

    • The task has multiple plausible interpretations.
    • Critique is cheap.
    • A judge can be calibrated.
    • Deterministic verification is unavailable.

    Debate is less useful when:

    • Code or math can be executed.
    • The judge is weak.
    • The agents share the same blind spot.
    • Latency/cost matters.

    Anthropic Multi-Agent Research System

    Core idea:

    Anthropic's production research system uses an orchestrator-worker pattern where a lead agent plans, creates specialized subagents, gathers results, and synthesizes a cited final answer.

    Important empirical claim:

    Anthropic reported that their multi-agent research system outperformed a single-agent baseline by 90.2% on an internal research eval for breadth-first research tasks.

    Teaching use:

    • This is the strongest production case study for multi-agent systems.
    • It also shows the conditions where multi-agent helps: broad research, independent search directions, parallel tool use, and concise result synthesis.

    Implementation details to teach:

    • Lead agent plans and stores plan in memory/checkpoint.
    • Lead agent spawns 3-5 subagents for complex breadth-first work.
    • Subagents use tools independently and return filtered findings.
    • A citation agent handles attribution separately.
    • Production reliability requires checkpoints, retry logic, observability, and careful prompt iteration.

    Failure modes Anthropic reported:

    • Too many subagents for simple queries.
    • Endless searching for nonexistent sources.
    • Overly verbose or wrong search queries.
    • Duplicate work across subagents.
    • Agents distracting each other with excessive updates.

    Teaching point:

    The win was not "agents chatting." The win was decomposition, parallel search, context isolation, and synthesis under strong orchestration.

    Cognition's "Don't Build Multi-Agents" Counterpoint

    Core idea:

    Cognition argued that multi-agent systems are often fragile for coding because context does not transfer cleanly. Parallel agents make independent decisions about style, edge cases, and implementation details, causing integration problems.

    Teaching use:

    • This is the essential counterweight to Anthropic.
    • It helps students avoid "multi-agent because it sounds advanced."

    Implementation lesson:

    For coding tasks, especially editing tasks, read-only subagents are safer than parallel writer agents. A main agent can preserve coherent decision-making while delegating noisy exploration.

    Good compromise:

    • Use subagents for read-only exploration, research, review, or test summarization.
    • Be cautious with multiple implementers editing overlapping files.
    • If parallel implementation is needed, isolate worktrees and assign disjoint ownership.

    LangChain Synthesis: When Multi-Agent Actually Helps

    Core idea:

    LangChain's post reconciled Anthropic and Cognition: both are mostly about context engineering. Multi-agent systems that primarily read are easier than systems that write.

    Teaching use:

    • Use this to conclude the debate.

    Decision rule:

    • Broad independent reading: multi-agent likely helps.
    • Coordinated writing: single agent or tightly controlled graph is usually better.
    • Parallel writing: only if work is cleanly separable and integration is explicit.

    11.3 Protocols and Standards as of May 2026

    MCP: Agent-to-Tools and Agent-to-Context Boundary

    MCP standardizes how LLM applications connect to external tools, prompts, and resources.

    Teach MCP as:

    • A protocol boundary between agent hosts and external context/tool servers.
    • Not a memory system by itself.
    • Not a multi-agent protocol by itself.
    • A way to expose enterprise systems safely and consistently.

    MCP concepts to teach:

    • Resources: data/context for the model or user.
    • Prompts: reusable templated workflows.
    • Tools: executable functions.
    • Lifecycle and capability negotiation.
    • Authorization for HTTP transports in later spec revisions.
    • Utilities such as logging, progress, cancellation, and error reporting.

    Enterprise implementation guidance:

    • Use MCP servers as controlled adapters to enterprise systems.
    • Do not expose broad database or shell access as one generic tool.
    • Put authorization and audit at the MCP server layer.
    • Treat tool descriptions as untrusted unless from trusted servers.
    • Require user approval for high-impact operations.
    • Use separate MCP servers per domain or permission boundary.

    Example:

    Agent Host
  -> HR MCP server: read employee policy, submit PTO request
  -> CRM MCP server: read account, draft note, update opportunity
  -> Code MCP server: read repo, run tests, create PR

    Bad enterprise MCP design:

    tool: execute_sql(query: string)
permissions: all tables, write access
approval: none

    Better design:

    tool: get_customer_summary(customer_id)
tool: list_open_support_cases(customer_id)
tool: draft_account_note(customer_id, note)
tool: request_account_update(customer_id, patch)  # approval required

    A2A: Agent-to-Agent Boundary

    A2A is an open protocol initiated by Google Cloud to let agents communicate across vendors, clouds, and frameworks.

    Teach A2A as:

    • A peer-agent interoperability protocol.
    • Useful when one enterprise agent needs to call another agent without knowing its internal implementation.
    • Complementary to MCP.

    Simple distinction:

    • MCP connects agents to tools and data.
    • A2A connects agents to other agents.

    Enterprise example:

    Procurement Agent
  -> uses MCP to read internal purchase policies
  -> uses A2A to ask Vendor Agent for quote status
  -> uses MCP to submit purchase request

    Enterprise risks:

    • Cross-boundary data sharing.
    • Unknown retention policies of external agents.
    • Authentication and authorization gaps.
    • Ambiguous accountability when an external agent acts incorrectly.

    Teaching point:

    Protocols reduce integration chaos, but they do not solve trust. Enterprise deployments still need identity, consent, audit, data classification, and policy enforcement.

    11.4 Real-World Implementation Patterns in 2026

    Pattern 1: Skills + Connectors + Subagents

    Anthropic's May 2026 financial-services agent templates are a useful current reference architecture:

    • Skills: domain instructions, workflows, and reusable procedures.
    • Connectors: governed access to market data, research platforms, internal repositories, CRMs, and productivity tools.
    • Subagents: specialized models for tasks such as research, valuation review, methodology checks, or document drafting.

    Teaching use:

    This is exactly the convergence of Classes 4, 6, and 7:

    • Skills are procedural memory.
    • Connectors are tool/context access.
    • Subagents provide context isolation and specialization.
    • Enterprise controls govern data access and review.

    Example enterprise translation:

    For an insurance claims agent:

    • Skills: claims triage playbook, fraud review checklist, regulatory response templates.
    • Connectors: policy admin system, claims database, document store, email, CRM.
    • Subagents: medical document summarizer, coverage analyst, fraud red-team reviewer, customer-response drafter.

    Pattern 2: Managed Agent Platform

    Microsoft Foundry Agent Service is representative of the managed enterprise direction:

    • Hosting and scaling.
    • Identity through Entra.
    • RBAC.
    • Private networking.
    • Content safety and prompt-injection mitigations.
    • Bring-your-own storage/search/state resources.
    • Tracing and evaluation.
    • Publishing through Teams, Microsoft 365 Copilot, and agent registries.

    Teaching use:

    This is what "production agent" means in an enterprise: runtime, identity, observability, governance, and distribution are first-class.

    Build-vs-buy discussion:

    Build from scratch when:

    • You are teaching fundamentals.
    • You need deep custom control.
    • You are still discovering the right architecture.

    Use managed platforms when:

    • You need enterprise identity and access controls.
    • You need compliance and data residency.
    • You need non-engineers to use the agent.
    • You need lifecycle management and monitoring.

    Pattern 3: Graph-Based Workflow Agent

    Use when:

    • The workflow has clear states.
    • Human approvals are required.
    • You need retries and resumability.
    • Auditability matters.

    Example graph:

    intake
  -> classify_request
  -> retrieve_context
  -> plan
  -> execute_read_only_tools
  -> if high_risk: human_approval
  -> execute_write_tool
  -> verify
  -> final_response
  -> memory_consolidation

    Implementation details:

    • Persist graph state after every node.
    • Store tool inputs/outputs as trace spans.
    • Separate read tools from write tools.
    • Require approval for writes above risk threshold.
    • Use deterministic checks before final response.

    Pattern 4: Read-Only Subagents for Enterprise Search

    Use when:

    • The main agent needs broad exploration.
    • Search traces would pollute context.
    • Workers can operate independently.
    • Final answer requires synthesis.

    Good use cases:

    • Legal research across many documents.
    • Security incident investigation across logs.
    • Codebase exploration.
    • Competitive intelligence.
    • Vendor due diligence.

    Worker output contract:

    {
  "task": "Find refund-policy constraints for EU customers",
  "findings": [
    {
      "claim": "EU customers may cancel within 14 days for digital services unless consent waiver was accepted.",
      "evidence": "policy/refunds/eu.md#section-2",
      "confidence": "high"
    }
  ],
  "uncertainties": [
    "Did not inspect country-specific exceptions for Germany."
  ],
  "recommended_next_step": "Ask policy specialist to verify Germany exception."
}

    Pattern 5: Reviewer / Critic Agents

    Use when:

    • A generated artifact needs quality control.
    • The reviewer can inspect evidence.
    • The reviewer has a different rubric or toolset.

    Examples:

    • Code reviewer checks diff and tests.
    • Compliance reviewer checks policy.
    • Security reviewer checks tool calls and data exposure.
    • Financial reviewer checks formulas and assumptions.

    Important:

    Reviewer agents should not be vague critics. Give them a rubric and require evidence.

    Reviewer output contract:

    {
  "decision": "approve | request_changes | block",
  "blocking_issues": [],
  "evidence_checked": [],
  "test_or_policy_gaps": [],
  "risk_level": "low | medium | high"
}

    11.5 Enterprise Blueprint: Adding Memory to Custom Agents

    Use this as a practical design recipe.

    Step 1: Define Memory Scopes

    At minimum:

    • User memory: preferences, communication style, stable user facts.
    • Account/customer memory: customer history, active contracts, support state.
    • Project memory: architecture, conventions, decisions.
    • Task memory: transient current run state.
    • Procedural memory: skills, playbooks, checklists.
    • Compliance memory: policies and rules, usually read-only.

    Rule:

    Never mix scopes casually. A user's preference should not become a company-wide rule. A project convention should not leak into another repo.

    Step 2: Define Memory Classes

    Use classes like:

    profile_fact
project_convention
decision_record
episodic_lesson
workflow_state
skill_candidate
policy_reference
customer_fact

    Each memory should carry:

    • id
    • type
    • scope
    • subject
    • content
    • source
    • created_at
    • updated_at
    • valid_from
    • valid_until or invalidated_at
    • confidence
    • sensitivity
    • owner
    • retention_policy

    Step 3: Decide What Is Always Visible

    Always-visible memory is expensive and powerful.

    Good candidates:

    • User communication preference
    • Current task goal
    • Current project brief
    • Safety policy summary
    • Tool-use boundaries

    Bad candidates:

    • Raw chat history
    • All previous tickets
    • Large documents
    • Old tool outputs
    • Low-confidence inferred facts

    Step 4: Add Retrieval

    Use hybrid retrieval:

    • Metadata filters first.
    • Keyword search for exact terms.
    • Embedding search for semantic similarity.
    • Reranking for final top-k.
    • Recency and validity filters.
    • Sensitivity filters based on user permissions.

    Retrieval budget:

    Set an explicit token budget for memory, for example 5-10% of context.

    Inject memory with wrappers:

    ## Retrieved Memory
Type: project_convention
Scope: repo:payments-service
Source: PROJECT_NOTES.md, updated 2026-05-10
Confidence: high
Why included: Current task edits a payment route.

Content:
Payment routes must emit audit events through `audit.log_payment_event`.

    Step 5: Add Memory Write Controls

    Memory writes are riskier than reads.

    Suggested policy:

    • Low-risk observations can be proposed automatically.
    • Medium-risk memory writes require review or delayed consolidation.
    • High-risk memory writes require human approval.
    • Sensitive memories require retention and deletion policy.
    • Memories derived from external untrusted content should be marked untrusted.

    Example:

    Allowed automatic write:
"User prefers concise status updates."

Needs review:
"Customer is likely to churn."

Disallowed without source:
"Customer violated contract terms."

    Step 6: Add Consolidation Jobs

    Run consolidation:

    • End of session
    • End of day
    • After resolved ticket
    • After merged PR
    • After high-value workflow completion

    Consolidation should:

    • Merge duplicates.
    • Mark contradictions.
    • Extract stable facts.
    • Separate facts from inferences.
    • Produce skill candidates only from verified success.
    • Archive raw traces.

    Step 7: Add Forgetting and Governance

    Enterprise memory must support:

    • Deletion
    • Retention windows
    • Legal hold
    • User data export
    • PII classification
    • Region/data residency constraints
    • Tenant isolation
    • Audit logs for reads and writes
    • "Why was this memory used?" explanations

    Teaching phrase:

    "In enterprise systems, memory is a regulated data product, not a scratchpad."

    11.6 Enterprise Blueprint: Adding Multi-Agent to Custom Agents

    Step 1: Start with One Agent and Instrument It

    Before adding agents, measure:

    • Where does it fail?
    • Does it run out of context?
    • Does it search too broadly?
    • Does it need review?
    • Does it wait on independent tasks?
    • Does it need different permissions at different phases?

    Only add agents to solve a measured bottleneck.

    Step 2: Choose the Multi-Agent Pattern

    Use this decision table:

    Problem Pattern
    Broad independent research Orchestrator + read-only research subagents
    Known business process Sequential or graph workflow
    Need quality control Worker + reviewer
    Need specialist ownership Supervisor + specialists
    Need cross-vendor collaboration A2A handoff
    Need external tools/data MCP tools/resources
    Need speed across independent subtasks Parallel fleet
    Need code edits in same files Usually stay single-agent

    Step 3: Define Agent Contracts

    Each agent needs:

    • Purpose
    • Inputs
    • Outputs
    • Tools
    • Permissions
    • Memory access
    • Stop condition
    • Error behavior
    • Escalation conditions

    Example:

    name: compliance-reviewer
purpose: Check whether a drafted customer response complies with policy.
tools:
  - read_policy
  - search_policy
memory_access:
  - read: policy_reference
  - read: customer_fact
  - write: none
forbidden:
  - send_email
  - update_customer_record
output:
  decision: approve | request_changes | block
  policy_citations: list
  required_edits: list

    Step 4: Use Least-Privilege Tools

    Separate read, draft, request, and commit tools.

    Bad:

    update_crm(any_object, any_patch)

    Better:

    get_account(account_id)
draft_account_note(account_id, note)
request_account_update(account_id, patch)
commit_account_update(approved_request_id)

    Tool permissions by role:

    • Researcher: read-only tools.
    • Drafter: read context and create draft artifacts.
    • Reviewer: read artifacts and policies.
    • Executor: write tools, but only after approval.
    • Auditor: trace and log access, no business action.

    Step 5: Add Handoff Filters

    Do not pass entire conversation history to every agent.

    Pass:

    • User objective
    • Relevant constraints
    • Required output schema
    • Relevant memory
    • Evidence or artifacts needed

    Remove:

    • Irrelevant tool traces
    • Other agents' failed attempts
    • Sensitive data not needed for the task
    • Hidden chain-of-thought

    OpenAI Agents SDK handoffs explicitly support input filters. Teach this as an important implementation detail: handoff is not just routing; it is context selection.

    Step 6: Add Guardrails at the Right Boundary

    Guardrail placement:

    • Input guardrails: before first agent handles user request.
    • Tool guardrails: before and after tool calls.
    • Handoff validation: before sending context to another agent.
    • Output guardrails: before final response leaves system.
    • Memory-write guardrails: before storing durable memory.

    Enterprise examples:

    • PII detector before sending context to external agent.
    • Policy check before invoking write tool.
    • Cost limit before spawning subagents.
    • Prompt-injection detector for retrieved web or email content.
    • Data-loss-prevention check before final answer.

    Step 7: Make Everything Observable

    Log and trace:

    • Agent selected
    • Prompt version
    • Model version
    • Tool calls
    • Tool arguments
    • Tool outputs or output hashes
    • Handoffs
    • Memory reads
    • Memory writes
    • Guardrail decisions
    • Human approvals
    • Final outcome
    • Cost and latency

    OpenAI Agents SDK and LangSmith both emphasize traces that include model calls, tools, handoffs, guardrails, and decision points. Teach students that production debugging is impossible without this.

    Step 8: Evaluate Before and After Multi-Agent

    Do not ship multi-agent because the demo looks good.

    Eval design:

    • Single-agent baseline.
    • Multi-agent candidate.
    • Same task set.
    • Same total token/dollar budget where possible.
    • Same tool permissions unless permission separation is the variable.
    • Measure both task success and failure modes.

    Enterprise metrics:

    • Resolution rate
    • Cost per resolved task
    • Human touches per task
    • Time to completion
    • Escalation rate
    • Incorrect action rate
    • Policy violation rate
    • Memory retrieval precision
    • Audit completeness
    • User satisfaction

    11.7 Enterprise Security and Governance

    Use OWASP and NIST to make security concrete.

    Relevant OWASP LLM Top 10 risks:

    • Prompt injection
    • Sensitive information disclosure
    • Supply chain vulnerabilities
    • Data/model poisoning
    • Improper output handling
    • Excessive agency
    • System prompt leakage
    • Vector and embedding weaknesses
    • Misinformation
    • Unbounded consumption

    For this lecture, emphasize:

    Prompt Injection

    Memory and multi-agent systems make prompt injection worse because malicious instructions can enter through:

    • User input
    • Retrieved documents
    • Emails
    • Web pages
    • Tool outputs
    • Other agents
    • Memory stores

    Mitigations:

    • Treat retrieved content as data, not instructions.
    • Separate trusted instructions from untrusted content.
    • Use tool allowlists.
    • Require approval for high-impact actions.
    • Sanitize and label external content.
    • Do not let untrusted content write durable memory without review.

    Excessive Agency

    Excessive agency means the system can do too much with too little oversight.

    Root causes:

    • Excessive functionality
    • Excessive permissions
    • Excessive autonomy

    Mitigations:

    • Least privilege tools.
    • Human approval for irreversible actions.
    • Narrow agent roles.
    • Transaction limits.
    • Dry-run modes.
    • Rate limits and cost budgets.
    • Reversible actions where possible.

    Vector and Embedding Weaknesses

    Memory systems and RAG introduce retrieval-specific risks:

    • Poisoned documents.
    • Similar but wrong memories.
    • Cross-tenant leakage.
    • Stale facts.
    • Embedding inversion or data leakage.

    Mitigations:

    • Tenant isolation.
    • Metadata filters.
    • Source trust scores.
    • Validity intervals.
    • Retrieval audit logs.
    • Memory conflict detection.

    NIST AI RMF / GenAI Profile

    Use NIST to frame enterprise governance:

    • Govern: roles, policies, accountability.
    • Map: use cases, context, data flows, affected users.
    • Measure: evals, monitoring, risk metrics.
    • Manage: mitigations, incident response, lifecycle controls.

    Class exercise:

    Ask students to map their memory-enabled multi-agent coding system to these four functions.

    11.9 How to Teach This in May 2026

    Update the lecture emphasis:

    • Do not present vector DB memory as the whole story. Present memory as lifecycle, governance, and retrieval policy.
    • Do not present multi-agent as "agents chatting." Present it as context partitioning, permission partitioning, and workflow control.
    • Present MCP and A2A as protocol boundaries, not magic architecture.
    • Present managed platforms as evidence that enterprise agent work is mostly runtime, identity, monitoring, and governance.
    • Present Anthropic and Cognition as compatible, not contradictory: multi-agent helps for broad read-heavy work; single-agent or tightly controlled workflows often win for coherent write-heavy work.

    Slide-worthy synthesis:

    Memory answers: What should persist across time?
Tools answer: What can the agent do?
Skills answer: How should repeated work be done?
Subagents answer: Which context should handle this part?
Protocols answer: Where are the trust boundaries?
Evals answer: Did any of this actually help?
