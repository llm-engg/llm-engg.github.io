Evaluating Agents

  • Earlier eval classes (eval module) covered single LLM calls

  • Agents break that assumption:

    • One task in, a sequence of steps out

LLM eval scores an answer. Agent eval must score a path.

  • When we evaluate an agent, we are evaluating the ability of the model and scaffold to work together to solve a task.

Outcome vs Trajectory Evaluation

Outcome eval Trajectory eval
What is scored Final answer / final environment state Every intermediate step
Question asked “Did it succeed?” “Did it succeed the right way?”
Cost Cheap, often automatable Expensive; needs traces + judges
Blind spot Lucky wrong paths Over-penalizes valid detours
Typical use Benchmarks (SWE-bench) Debugging, safety, policy checks

Agent Evaluation Harness

  • Evaluation : Set of tests that provide inputs to our agent system, collect outputs, and apply grading logic to determine whether the agent was successful
  • Agent evaluations are different : mutlitple chat turns, involve interacting with tools and the external environment
  • Evaluation harness : Similar to agent harness, manages the entire end-to-end process of evaluation.

Evaluation Components

  • Tasks - Individual test cases for the agent with predefined input and output criteria.

  • Trials - Each attempt at solving a task, we often run several trials for each task to ensure consistent results.

  • Trace / Trajectory - Complete transcript that includes outputs, tool calls, reasoning steps, intermediate outputs, or any other interactions from the agent during the trial.

  • Outcome - The final state of the external environment after a trial completes

  • Grader - Verifies the agent’s transcript or outcome by applying checks.

  • Metrics - what you record on every trial whether or not it passed, because “it worked” and “it worked in 4 turns for $0.02” are different results.

There may be multiple graders, compute performance metrics by aggregating across tasks and trials. Consider the outcome not just model outputs.

Do we need Evals

  • You can get surprisingly far without them - manual testing, dogfooding and intuition carry a prototype a long way. Early on, rigorous evals genuinely do feel like overhead that slows shipping.

  • The breaking point is production + scale - users report the agent “feels worse” after a change, and the team has no way to check but guess-and-check.

  • Without evals, debugging is reactive - wait for complaints, reproduce by hand, fix, hope nothing else regressed.

  • What you cannot do without them - tell a real regression from noise, test a change against hundreds of scenarios before shipping, or prove an improvement actually improved something.

Why Build Evals : Beyond Catching Regressions

  • They force you to define success - two engineers read the same spec and handle edge cases differently. The eval suite is where that ambiguity gets resolved, in writing.

  • They set your speed of model adoption - when a stronger model ships, teams without evals spend weeks testing; teams with evals tune prompts and upgrade in days.

  • Baselines come free - latency, token usage, cost per task and error rate, all tracked on a static bank of tasks.

  • Highest-bandwidth channel between product and research - an eval turns “make it better” into a metric someone can optimize against.

Useful at every stage: early they encode what the agent is supposed to do; later they hold the quality bar while it changes.

Example Eval Setups

  • Claude Code - shipped first on employee and user feedback, then added evals for narrow behaviours (concision, file edits), then for hard ones (over-engineering). Evals sit alongside production monitoring, A/B tests and user research - not instead of them.

  • Descript (video editing) - three dimensions of a good edit: don’t break things, do what I asked, do it well. Evolved manual grading -> LLM graders with product-written criteria + periodic human calibration. Runs two suites: quality benchmarking and regression.

  • Bolt - started late, on an agent already widely used. Three months to build a system that runs the agent, grades with static analysis, drives the app with browser agents, and uses LLM judges for instruction following.

Some teams start with evals; others add them once the absence becomes the bottleneck. Both paths work - the mistake is assuming you will never need them.

Human Graders

  • BEST source of truth for measuring quality.

  • Start with manual inspections performed by developers, researchers or by internal users

  • Create detailed rubric to define the key quality dimensions and how these criteria should be evaluated

  • Claude Code mention that their evaluation process began with human evaluation trials with internal Anthropic employees

Human Grading Calibration

Code-based Graders

  • Heuristic checks that can be captured in code
  • Reference-based (i.e. require ground truth), inflexible and can lack nuance, making them somewhat limited.

Model-based Graders

  • Prompt an LLM to evaluate some aspect of quality for us using LLM-as-a-Judge

Holistic Approach to Evaluation

  • Combine methods: automated evals for fast iteration, production monitoring for ground truth, and periodic human review for calibration

Case Study - The τ-bench Series

  • τ -bench (V1, V3), a benchmark emulating dynamic conversations between a user (simulated by language models) and a language agent provided with domain-specific API tools and policy guidelines

  • Agents are expected to do the following:

    • Interact with the user and resolve intent.

    • Adhere to a set of written policies or rules for each domain.

    • Use tools to retrieve data and modify the external environment.

Roadmap for Agent Evaluation - I

Step by step process for evals:

    1. Define success : Deatiled criteria on what it means for the agent to succeed

    • Outcome goals that verify aspects of the outcome (e.g., whether the expected database entries for the task were created).

    • Process goals that verify components of the transcript (e.g., whether certain tools were called).

    1. Collect a small task set -manually curate 10 to 20 initial tasks by considering realistic use cases
    1. Create useful tasks - create high-quality tasks that test important aspects of agent behavior
    1. Provide ground truth and reference - reference solution or known-good trajectory that proves the task is solvable and verifies that the grader is checking the right behavior
