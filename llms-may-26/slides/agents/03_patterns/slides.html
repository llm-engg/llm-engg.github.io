ReAct + Planning (Plan-then-Execute)

User -> Planner LLM -> Plan -> Executor LLM -> Tool -> ... -> Answer

Implementation

Plan Mode: AI analyzes requirements, reads codebase, builds a step-by-step plan. No modifications are made. The user reviews the plan.

Act Mode: AI executes the plan, editing files and running commands. Human approval at each step.

ReAct + Reflection

User -> LLM -> Tool -> ... -> LLM -> Draft Answer -> Critic LLM ->
  [if good: return]
  [if bad: feedback -> LLM -> retry]

Implementation

def react_with_reflection(task: str, max_reflections: int = 3):
    draft = basic_react_loop(task)

    for attempt in range(max_reflections):
        critique = critic_llm.generate(
            system="Evaluate this output. Is it complete, correct, well-structured? "
                   "If not, explain what needs improvement.",
            user=f"Task: {task}\nOutput: {draft}"
        )

        if critique.is_satisfactory:
            return draft

        # Retry with feedback
        draft = basic_react_loop(
            f"Original task: {task}\n"
            f"Previous attempt: {draft}\n"
            f"Feedback: {critique.feedback}\n"
            f"Please improve based on this feedback."
        )

    return draft  # Best effort after max reflections

Examples : CrewAI, LangGraph

Planning : How Do You Decompose?

The planner slide above assumes a plan exists. Producing one is its own design decision.

Axis Option A Option B
When Top-down — full plan before acting Opportunistic — plan the next step or two, re-plan as you learn
Shape Linear — ordered list of steps DAG — explicit dependencies, parallelisable branches
Ownership Plan is fixed; failures retry a step Plan is mutable; failures re-plan

Plan-and-Solve (Wang et al., 2023) is the cheapest version of this: no separate planner model, no orchestration — just prompt the model to “devise a plan, then carry out the subtasks” before answering.

A useful reference point: much of what a planner buys you, a better prompt buys you for free.

Reflexion — learning across attempts

Shinn et al. (2023) — Reflexion: Language Agents with Verbal Reinforcement Learning

The retry loop we just saw throws away what it learned. Reflexion keeps it.

attempt 1 → fail → write a verbal self-reflection → store in memory
attempt 2 → read reflections → fail differently → reflect again → store
attempt 3 → read reflections → succeed
  • The reflection is natural language, not a gradient — hence “verbal” reinforcement
  • It persists in an episodic buffer across episodes, not just within one retry
  • No weights change. The learning lives entirely in the context

This is where reflection stops being error-handling and starts being memory — which is exactly the thread deck 07 picks up.

Self-Refine — critique with no external signal

Madaan et al. (2023) — Self-Refine: Iterative Refinement with Self-Feedback

One model, three roles: generate → critique its own output → revise. No test suite, no verifier, no second model.

When this works: the task has qualities the model can recognise better than it can produce in one pass — tone, completeness, structure, readability.

When it fails: anything the model cannot check. It will happily “refine” a wrong answer into a differently wrong answer, with confidence.

Reflexion vs Self-Refine

Self-Refine Reflexion
Signal The model’s own judgement An outcome — test failed, task unsolved
Scope Within one attempt Across attempts
Persists? No Yes — episodic memory buffer
Fails when The model can’t judge the task No usable outcome signal exists

The distinction that matters: is there a ground-truth signal? With one, use Reflexion. Without one, self-critique is the model marking its own homework.

Verification — who actually checks the work?

Ranked by how much you should trust them:

  1. Tool-grounded — tests pass, the code compiles, the API returned 200. Ground truth.
  2. Deterministic checks — schema validation, linters, invariants. Cheap and reliable.
  3. Model-based verifier — a second model scores the output. Useful, fallible.
  4. Self-critique — the same model judges itself. Weakest, and the default people reach for.

Push verification down this list wherever you can. A failing pytest is worth more than any amount of critique prose — and it costs one tool call instead of a model round trip.

Search-Based Planning — when greedy isn’t enough

ReAct is a greedy planner: it commits to each action as it goes, and cannot un-commit.

  • Tree of Thoughts (Yao et al.) — branch over reasoning steps, evaluate, prune
  • LATS (Zhou et al.) — MCTS over action sequences; combines search, reflection and value estimation

Search buys recovery from bad early commitments — which is exactly what greedy loops cannot do.

Search costs a multiple of the token spend, since most explored branches are discarded.

Worth it when early decisions constrain everything downstream (planning, puzzles, irreversible actions) and the task is hard enough to justify it. Rarely worth it otherwise.

The Planning Paradox

More structure is not free, and it is not monotonic:

  • Every planner call is tokens and latency the greedy loop didn’t spend
  • A plan written before acting is a plan written with the least information you will ever have
  • Rigid plans resist the thing agents are good at — noticing mid-task that the approach is wrong

The through-line question, made concrete: on an easy task the planner is worse than ReAct. There is a crossover point where difficulty makes structure pay. Nobody can tell you where it is for your workload — you have to measure it.

Example : SmolAgents

Advantages:

  • Can compose multiple tools in one step (regular tool calling does them one at a time)
  • Can use conditionals, loops, variables within one “action”
  • More natural for code-trained LLMs
  • Fewer round-trips to the API

Limitations:

  • Arbitrary code execution requires robust sandboxing
  • Harder to audit than structured tool calls
  • Error messages can be opaque

Event-Driven / Stream-Based / Graph Based

Event Driven

Event Stream -> Agent subscribes -> Processes events -> Emits new events

Used By: AG2 (MemoryStream), CrewAI Flows

Graph-Based State Machine

Nodes = agents/functions
Edges = transitions (can be conditional)
State = immutable, checkpointed after every node

Used by: LangGraph, Google ADK 2.0

Heartbeat / Proactive Loop

Cron triggers agent 
  -> Agent checks task list 
  -> [nothing to do: HEARTBEAT_OK (suppressed)]
  -> [something to do: execute -> notify user]

Examples - OpenClaw, Hermes Agent

Implementation:

# Pseudo-code for OpenClaw's heartbeat
@cron("*/30 * * * *")  # Every 30 minutes
def heartbeat():
    context = assemble_context(
        agents_md=read("AGENTS.md"),
        soul_md=read("SOUL.md"),
        tasks=read("tasks.md"),
        memory=search_memory("pending tasks")
    )

    response = llm.generate(
        system=context,
        user="Check your task list. If anything needs attention, "
             "handle it and report. Otherwise reply HEARTBEAT_OK."
    )

    if "HEARTBEAT_OK" in response:
        return  # Gateway suppresses, user sees nothing

    gateway.send_to_user(response)  # User gets notified

Human in the Loop (HITL) Pattern

Extends another pattern (typically ReAct), but adds a validation step prior to taking an action, where the agent seeks human feedback or approval before proceeding with certain actions.

Example: - An agent that performs sensitive actions, such as sending emails or making financial transactions

Agent Orchestration Pattern

  • Multiple agents with different capabilities are orchestrated together to achieve a common goal

Example: - Software development agent that uses multiple specialized agents for code generation, testing, and deployment

Model-Centric to System-Centric Thinking

  • Previous classes: Architecture, GPUs, Inference and Evaluation - LLM was central
  • Current focus: Overall system design, where LLM is a critical component but not the only one
    • Control flow (the loop)
    • State management (context, soon memory)
    • I/O interfaces (tools)
    • Safety properties (bounds, sandboxing)
    • Observability (tracing, logging)

When not to use an Agent

  1. Is the task structure stable? If the steps are the same every time, it’s a pipeline.
  2. Is there a small fixed branch set? (≤5 known branches.) It’s a workflow with an LLM router.
  3. Is the search space large but the verifier cheap? It’s best-of-N over generations.
  4. Does the LLM need to decide what to do based on what it just saw? Needs an Agent.

Repo-question decision:

A stable “find files -> retrieve chunks -> answer” system is a pipeline/RAG app. It becomes agentic when the model chooses follow-up searches, reads, tests, or stops based on observations.

Concrete examples

Task Best tool Why
Extract structured fields from invoices LLM call with JSON schema Single call, no decision
RAG QA over a fixed corpus Pipeline (retrieve -> rerank -> answer) Steps are fixed
Customer support routing across 8 categories Workflow (LLM router -> category-specific handler) Bounded branches
Multi-step research across a changing web Agent The next step depends on the last result
Coding assistant on an unfamiliar repo Agent The whole point is exploration
