Compute Spend

Note

Training is a one-time cost; inference is a recurring cost - accounting for 80-90% of total compute spend.

Inference vs Training

Training

  • Weight updates via backprop & gradient descent
  • Parallelizable across sequence length
  • Optimized for throughput
  • Memory: weights + gradients + optimizer states + activations
  • \(\approx\) 4-6x model size (FP16)

Inference

  • Samples tokens from learned distributions - no weight updates
  • Optimized for latency (TTFT, ITL) and throughput simultaneously
  • Memory: weights + KV cache + forward pass activations
  • \(\approx\) 1-1.5x model size at short context; can grow much larger when KV cache dominates

LLM Inference Challenges

Why is LLM inference harder than standard neural network inference?

  • Variable-length compute : inputs and outputs have no fixed tensor shapes
  • Batching is difficult : sequences finish at different times
  • Need to balance TTFT, ITL, and throughput simultaneously

LLM Inference Challenges

Why is LLM inference harder than standard neural network inference?

  • Two distinct phases: prefill (compute-intensive) vs decode (memory-intensive)
  • Two different compute characteristics -> need different optimizations

Memory : KV Cache

Multi-Head Attention Overview

\(\text{Attention}(Q, K, V) = \text{softmax}\left(\frac{QK^T}{\sqrt{d_k}}\right)V\)

\[\text{MultiHead}(Q, K, V) = \text{Concat}(\text{head}_1, \dots, \text{head}_h)W^O\]

Scaled Dot-Product Attention:

  • \(Q, K, V\): Query, Key, and Value matrices derived from input embeddings
  • \(d_k\): The dimensionality of the keys (and queries)
  • \(W^O\): Output projection matrix that combines the outputs of all heads into a single vector.
  • \(h\): The number of parallel attention heads.

KV Cache - Illustration

Step Tokens in cache Per-layer cache
Prefill (S=5) t1 … t5 \(5 \times K \times H\) (×2: K and V)
Decode step 1 t1 … t6 append 1 row
Decode step 2 t1 … t7 append 1 row

Note

The cache grows linearly with sequence length: long context is expensive in memory even though each new token is cheap in compute. This single fact motivates every attention variant that follows.

MHA - Generation Phase

Generation Phase (Autoregressive Decoding):

  • Generate tokens one at a time autoregressively
  • At each step, compute attention over all previously generated tokens
  • Keys and Values for past tokens remain unchanged
  • Only the new token’s Query needs to attend to all previous Keys/Values

MHA - Generation Phase

Problem: Without caching, we recompute K and V for all previous tokens at every step!

  • Step 1: Compute K, V for token 1
  • Step 2: Recompute K, V for tokens 1, 2
  • Step 3: Recompute K, V for tokens 1, 2, 3
  • …
  • Step N: Recompute K, V for all N tokens → O(N²) redundant computation

Solution: KV Cache — Store computed K and V vectors and reuse them

KV Cache

  • Reduced per-token compute from O(N) to O(1) by caching K and V for all past tokens
  • Reduced TTFT, increased throughput

Grouped-Query Attention (GQA)

Key Insight: Use 1 KV head for each group of query heads (e.g., 1 KV head for 8 query heads)

  • Balance between MHA (full expressivity) and MQA (maximum efficiency)
  • If 8 Query heads share 1 KV head
Attention Type Memory per Token
MHA 4 MB
MQA 32 KB
GQA 500 KB

8× reduction compared to MHA, while preserving more expressivity than MQA

Multi-head Latent Attention (MLA)

Key Insight: Compress K and V into a low-dimensional latent vector before caching

  • Project hidden states into a compressed latent representation \(c^{KV}\) (e.g., 512 dims)
  • Cache only the compressed latent, not full K and V
  • Reconstruct K and V from latent during attention computation

The Key Question

Is GPU spending its time doing compute or waiting for data?

To answer this, we need to understand:

  1. Arithmetic Intensity - how much compute per byte of memory accessed
  2. The Roofline Model - what limits the GPU’s performance
  3. How prefill and decode differ - why decode is memory bound

Arithmetic Intensity

\[\text{Arithmetic Intensity} = \frac{\text{Compute FLOPs}}{\text{Memory Bytes}}\]

AI tells you whether the model is spending time computing (doing math) or fetching (moving data).

  • Low AI = GPU mostly waiting for data.
  • High AI = GPU mostly doing useful computation.

Tip

Intuition : “Imagine you’re a cook. The fridge (HBM) is in the next room. Arithmetic intensity is how many dishes you can prepare per trip to the fridge.

  • If AI=1, you grab one ingredient, cook one dish, walk back. Terrible.
  • If AI=100, you grab one ingredient and cook 100 dishes. Great!”

Arithmetic Intensity

Setup: Matrix multiply in a linear layer : \(Y = X \cdot W\)

B : batch size, D : hidden dimension, F : feedforward dimension

\(X\): B \(\times\) D, \(W\): D \(\times\) F

FLOPs = \(2 \cdot B \cdot D \cdot F\)

Bytes transferred:

  • Read X: \(B \cdot D \cdot 2\)
  • Read W: \(D \cdot F \cdot 2\)
  • Write Y: \(B \cdot F \cdot 2\)

Total Bytes = \(2(BD + DF + BF)\)

\[\text{AI} = \frac{2 \cdot B \cdot D \cdot F}{2(BD + DF + BF)}\]

\[= \frac{B \cdot D \cdot F}{BD + DF + BF}\]

If \(B \ll D, F\):

\[\text{AI} \approx \frac{B \cdot D \cdot F}{D \cdot F} = B\]

Arithmetic intensity \(\approx\) batch size (when B is small relative to model dimensions)

Arithmetic Intensity

Batch Size = 1 (single-stream decode)

\[ \text{AI} = \frac{2 \cdot D \cdot F}{2 \cdot D \cdot F + 2 \cdot D + 2 \cdot F} \approx 1 \text{ FLOP/byte}\]

You read the entire weight matrix (\(D \times F\))…

…but only do one row’s worth of compute

For A100 GPU (Capacity : 150-200 FLOPs/byte):

  • AI \(\approx\) 1 \(\ll\) 150-200
  • Peak-compute upper bound: < 1% of peak FLOPs
  • The GPU is basically spending all its time waiting for data to arrive from memory, not doing math.

The Roofline Model

Performance is bounded by:

  1. Compute : how fast GPU does math (FLOPs/s)
  2. Bandwidth : how fast data moves (GB/s)
  3. Capacity : whether weights + KV cache fit at all (GB)

Note

Knee point = bandwidth-bound to compute-bound transisiton -> minimum AI needed to fully utilize GPU’s compute.

Figure: an example roofline plot showing two algorithms with different arithmetic intensities (Algo 1 and Algo 2) and their corresponding theoretical peak throughput under different bandwidths (BW1 and BW2). In the red area, an algorithm is bandwidth bound at both bandwidths and is wasting some fraction of the hardware’s peak FLOPs/s. The yellow area is bandwidth-bound only at the lower bandwidth (BW1). The green area is compute-bound at all bandwidths.

\[\text{Performance} = \min(\text{Peak FLOPs}, \text{AI} \times \text{BW})\]

Prefill vs Decode

Prefill

  • Process all prompt tokens at once
  • T = S (hundreds/thousands)
  • Parallelizable
  • Compute-bound (high AI)
  • Fills the KV cache
  • Determines TTFT

Decode

  • Generate tokens one at a time
  • T = 1
  • Sequential (autoregressive)
  • Memory-bound (low AI)
  • Reads from & appends to KV cache
  • Determines per-token latency (ITL)

MLP Layer: Computing Arithmetic Intensity

\[Y = \left(\text{GeLU}(X \cdot W_{\text{up}}) \odot (X \cdot W_{\text{gate}})\right) \cdot W_{\text{down}}\]

Step Operation FLOPs Bytes
1 Read X (B×T×D) — \(2 \cdot B \cdot T \cdot D\)
2 Read \(W_{\text{up}}, W_{\text{gate}}, W_{\text{down}}\) — \(3 \cdot 2 \cdot D \cdot F\)
3 \(X \cdot W_{\text{up}}\) \(2BTDF\) \(2BTF\)
4 \(X \cdot W_{\text{gate}}\) \(2BTDF\) \(2BTF\)
5 GeLU+element-wise+\(W_{\text{down}}\) \(2BTDF\) \(2BTD\)

FLOPs = \(6 \cdot B \cdot T \cdot D \cdot F\)

Bytes = \(4BTD + 6DF + 4BTF\)

\[\text{AI}_{\text{MLP}} = \frac{6BTDF}{4BTD + 6DF + 4BTF} \approx B \cdot T \quad \text{(when } BT \ll D, F\text{)}\]

Important

Increase batch size (B) and sequence length (T) to increase AI and move from memory-bound to compute-bound regime for MLP layers.

MLP AI: Prefill vs Decode

Prefill (T = S)

\[\text{AI}_{\text{MLP}} \approx B \cdot S\]

Compute-bound

  • S = 1024, B = 1 : AI ≈ 1024
  • Well above knee point (~200)

Decode (T = 1)

\[\text{AI}_{\text{MLP}} \approx B\]

Memory-bound (BAD)

  • B = 1 => AI ≈ 1, B = 32 => AI ≈ 32
  • Far below knee point

Important

During decode, ALL model weights are read from HBM for every single output token, but only do one token’s worth of matmuls. GPU utilization: 1-5% of peak FLOPs.

Attention Layer: Arithmetic Intensity

Step Operation FLOPs Bytes
1 Read Q, K, V — \(2BTD + 4BSD\)
2 \(A = Q \cdot K^T\) \(2BSTD\) —
3 \(Y = \text{softmax}(A) \cdot V\) \(2BSTD\) —
4 Write Y — \(2BTD\)

\[\text{AI}_{\text{attn}} = \frac{4BSTD}{4BTD + 4BSD} = \frac{S \cdot T}{S + T}\]

Prefill (T = S):\[\text{AI} = \frac{S^2}{2S} = \frac{S}{2}\] S=1024 => AI ≈ 512

Attention Layer: Arithmetic Intensity

Step Operation FLOPs Bytes
1 Read Q, K, V — \(2BTD + 4BSD\)
2 \(A = Q \cdot K^T\) \(2BSTD\) —
3 \(Y = \text{softmax}(A) \cdot V\) \(2BSTD\) —
4 Write Y — \(2BTD\)

\[\text{AI}_{\text{attn}} = \frac{4BSTD}{4BTD + 4BSD} = \frac{S \cdot T}{S + T}\]

Decode (T = 1): \[\text{AI} = \frac{S}{S+1} < 1\] Always < 1 regardless of S!

Summary: Arithmetic Intensity

Stage MLP AI Attention AI Regime
Prefill (S=1024, B=1) ~1024 ~512 Compute-bound
Prefill (S=4096, B=1) ~4096 ~2048 Compute-bound
Decode (T=1, B=1) ~1 <1 Memory-bound
Decode (T=1, B=32) ~32 <1 MLP less bad, attn still memory-bound
Decode (T=1, B=256) ~256 <1 MLP compute-bound, attn still bad
  • Prefill is compute-limited; limited by GPU FLOPs
  • Decode is memory-limited ; limited by memory bandwidth
  • MLP intensity ~ \(B \cdot T\), Attention intensity ~ \(\frac{S \cdot T}{S + T}\)

Important

To overcome this, large models are served in Dis-aggregated fashion. Prefill anbd Decode happens on separate chips or servers

Inference Metrics

User-facing:

  • TTFT : Time to First Token - How long user waits for the first word to appear. Dominated by prefill time.

  • ITL : Inter-Token Latency (Streaming speed) - how fast words appear after the first one (seconds/token).

System-facing: - - Throughput : Total tokens the system can produce per second across all users (tokens/sec).

Use Case TTFT ITL Throughput

Key Inference Optimizations

Most optimizations map to one of four strategies:

  1. Read less data per token
    • Quantization (smaller weights), GQA/MLA (smaller KV cache), pruning
  2. Do more useful work per data read
    • Batching (amortize weight reads), kernel fusion (fewer HBM round trips)
  3. Generate more tokens per forward pass
    • Speculative decoding (verify N tokens in one pass instead of generating 1)
  4. Schedule / place work better
  • Continuous batching, prefix caching, prefill/decode disaggregation

The One Formula to Remember

\[\text{Decode tokens/sec} \approx \frac{\text{Memory Bandwidth (GB/s)}}{\text{Model Size (GB)} + \text{KV Cache Overhead (GB)}}\]

Three numbers determine decode performance:

  1. Model size in bytes (reduce with quantization)
  2. KV cache size (reduce with GQA, MLA, sliding window)
  3. Memory bandwidth of GPU (more the better)
