The Roofline Model

Performance is bounded by:

  1. Compute : how fast GPU does math (FLOPs/s)
  2. Bandwidth : how fast data moves (GB/s)
  3. Capacity : whether weights + KV cache fit at all (GB)

Note

Knee point = bandwidth-bound to compute-bound transisiton -> minimum AI needed to fully utilize GPU’s compute.

Inference Tradeoffs

Cannot optimize for all three simultaneously.

Three way tradeoff between accuracy, latency, and cost

Priority Tradeoff Engineering Bridges
Accuracy + Low Latency Higher cost Use smaller models to reduce serving cost; recover accuracy with RAG, fine-tuning, and tool use. Quantization cuts GPU memory footprint further.
Accuracy + Low Cost Higher latency Batch inference, async pipelines, and queue-tolerant architectures absorb the latency gracefully.
Low Latency + Low Cost Accuracy at risk Smaller or distilled models with quantization; improve accuracy via RAG, fine-tuning

Static Batching / Request-Level Batching

Traditional systems use static batching to improve GPU utilization:

  • Group incoming requests into fixed-size batches (e.g., 8, 16, 32)
  • Process each batch in parallel on the GPU
  • High GPU utilization for large batches

Drawbacks:

  • No early return and tail latency dictated by longest sequence in the batch
  • Internal fragmentation from padding to max sequence length
  • GPU utilization: 30-40% for small batches, drops to 10-20% for larger batches (padding + waiting on the longest) due to padding overhead

Continuous Batching

Orca : A Distributed Serving System for Transformer-Based Generative Models, 2022

  • Do dynamic batching of requests as they arrive
  • Process batching at token level instead of request level
  • Early return as soon as a request in the batch finishes
  • Support for token-level interleaving of requests

Continuous Batching

Continuous Batching

Continuous Batching:

  • Dynamically batch requests at the token level, allowing for early return and better GPU utilization.
  • As soon as one request in the batch finishes generating its next token, it can be returned to the client, while the remaining requests continue processing.

Early finished and late arrived requests are handled much more efficiently. The server can immediately return results for completed requests without waiting for the entire batch to finish, significantly reducing tail latency and improving user experience.

Continuous Batching Mechanics

The Loop:

  1. Selection: Choose candidate requests for next iteration
  2. Batch Formation: Combine prefill chunks and decode tokens
  3. Forward Pass: Run model on current batch
  4. Completion Check: Identify finished sequences
  5. Admission: Add new requests from queue
  6. Iteration: Repeat

Benefits:

  • No Waiting: Short requests exit immediately, don’t wait for long ones
  • GPU Saturation: Keep compute units busy 80%+ of time

Chunked Prefill

A large prefill can dominate an iteration and spike latency for decode requests.

Chunked prefill addresses this:

  • Split large prefills into chunks (e.g., 512 tokens at a time)
  • Interleave prefill chunks with decode steps
  • Prevents a single large prefill from blocking decode for all other requests

This is now standard in vLLM (enabled by default) and SGLang.

Scheduling Policies

Scheduling

  • First-Come-First-Served (FCFS)

  • Priority-Based

  • Longest Prefix Match (LPM)

Preemption Strategies:

  1. Swap: Move KV cache to CPU memory when preempting

  2. Recompute: Discard KV cache, regenerate when resuming

    • Cost: 2× compute for the prompt
    • Benefit: No memory bandwidth cost for swap

Rule of Thumb: Swap for long sequences (KV cache >> compute cost), recompute for short sequences.

KV Cache

KV Cache

Generation Phase (Autoregressive Decoding):

  • Generate tokens one at a time autoregressively
  • At each step, compute attention over all previously generated tokens
  • Keys and Values for past tokens remain unchanged
  • Only the new token’s Query needs to attend to all previous Keys/Values

KV Cache

KV Cache

Problem: Without caching, we recompute K and V for all previous tokens at every step!

  • Step 1: Compute K, V for token 1
  • Step 2: Recompute K, V for tokens 1, 2
  • Step 3: Recompute K, V for tokens 1, 2, 3
  • …
  • Step N: Recompute K, V for all N tokens → O(N²) redundant computation

Solution: KV Cache — Store computed K and V vectors and reuse them

KV Cache

  • Reduced per-token compute from O(N) to O(1) by caching K and V for all past tokens
  • Reduced TTFT, increased throughput

KV Cache with Attention Variants

Per-token KV cache memory formula:

\[\text{KV}_{\text{per token}} = 2 \times n_{\text{layers}} \times n_{\text{kv heads}} \times d_{\text{head}} \times \text{dtype bytes}\]

Memory Waste from KV Cache

  • Internal fragmentation: over-allocated due to the unknown output length
  • Reservation: not used at the current step, but used in the future
  • External fragmentation: due to different sequence lengths

Paged KV Cache

Paged KV Cache

vLLM PagedAttention : Efficient Memory Management for Large Language Model Serving with PagedAttention

Inspired by virtual memory management in operating systems:

  • Allocate KV cache in smaller pages (e.g., 1K tokens)
  • Dynamically map pages to active requests
  • Reduced internal fragmentation

Paged KV Cache

Paged KV Cache

  • Logical blocks: The model’s attention mechanism operates on the entire context as a single logical block (e.g., a 16K token context treated as one block for attention computations).

  • Physical blocks (pages): Memory is divided into smaller physical blocks/pages (e.g., 16–32 tokens each), dynamically allocated and mapped to different requests as needed.

Paged KV Cache - Multiple Requests

Paged KV Cache - Multiple Requests

  • Each request’s KV cache is divided into multiple physical blocks (pages) that can be allocated independently.
  • Multiple requests can share the same physical blocks if they have similar context lengths, improving memory efficiency and GPU utilization.

Paged Attention

Paged Attention

  • PagedAttention allows storing continuous keys and values in non-contiguous memory space
  • During the attention computation, the PagedAttention kernel identifies and fetches different KV blocks separately
  • Computes attention across these non-contiguous blocks
  • This is done in a custom CUDA kernel optimized for the block-table lookup pattern

Memory Efficiency of Paged KV Cache

Minimizes internal fragmentation

  • Only happens at the last block of a sequence
  • #num wasted tokens per sequence < block size
  • Seq len: O(100) – O(1000) tokens
  • Block size: 16 or 32 tokens
  • No external frgmentation
  • On average,wasted space < 4% ofKV cache

Using vLLM

Python Class

pip install vllm
from vllm import LLM
# Example prompts.
prompts = ["Hello, my name is", "The capital of France is"]
# Create an LLM with HF model name.
llm = LLM(model="meta-llama/Meta-Llama-3.1-8B")
# Generate texts from the prompts.
outputs = llm.generate(prompts)

OpenAI-compatible server

# Start the vLLM server.
vllm serve meta-llama/Meta-Llama-3.1-8B

# Send a request to the server.
curl http://localhost:8000/v1/completions \

-d '{

"max_tokens": 7,
"temperature": 0

Key Config Options

Key configuration parameters:

  • --gpu-memory-utilization 0.90: Fraction of GPU memory to use for KV cache (default 0.9)
  • --max-model-len 4096: Maximum sequence length
  • --block-size 16: Number of tokens per KV block
  • --tensor-parallel-size N: Number of GPUs for tensor parallelism
  • --enable-prefix-caching: Enable automatic hash-based prefix caching
