How do we know any of it works?

Bridge: From Output Eval to Agent Eval

Earlier eval classes (eval module) covered single LLM calls:

  • Golden sets, reference-based metrics, LLM-as-judge
  • One prompt in, one answer out, score the answer

Agents break that assumption:

  • One task in, a sequence of steps out
  • The final answer is only the last frame of the film

Output eval scores an answer. Agent eval must score a path.

Why Agent Eval Is Different

  • Non-determinism: same task, same agent, different runs
  • Branching trajectories: many paths reach the goal; some paths reach it by accident
  • Compounding errors: a step-2 mistake poisons every step after it
  • Side effects: the agent changed the world (files, databases, emails) along the way
  • Partial completion: 9 of 10 subtasks done is not 90% credit — and sometimes it is

There is no single “output” to grade. There is a trace, an environment diff, and an outcome.

Compounding Errors, Revisited

From deck 08: if each step succeeds with probability \(p\), an \(n\)-step chain succeeds with \(p^n\).

\[0.9^5 \approx 59\% \qquad 0.9^{20} \approx 12\%\]

Implications for eval:

  • Per-step accuracy and end-to-end success are different numbers
  • Long-horizon tasks fail even when every individual step “looks fine”
  • An eval that only checks the final state hides where the chain broke

Trajectory eval exists to find the broken link, not just the broken chain.

Outcome vs Trajectory Evaluation

Outcome eval Trajectory eval
What is scored Final answer / final environment state Every intermediate step
Question asked “Did it succeed?” “Did it succeed the right way?”
Cost Cheap, often automatable Expensive; needs traces + judges
Blind spot Lucky wrong paths Over-penalizes valid detours
Typical use Benchmarks (SWE-bench) Debugging, safety, policy checks

Outcome eval tells you that the agent failed. Trajectory eval tells you why — and catches the runs that “succeeded” but should not have.

When Outcome-Only Is Enough

Outcome eval suffices when:

  • The answer is verifiable: unit tests pass, exact match, numeric equality
  • Side effects don’t matter or are sandboxed away
  • You need a leaderboard number, not a debug signal

Trajectory eval becomes mandatory when:

  • Safety/policy: agent must not call certain tools, exfiltrate data, or exceed budget — even if the answer is right
  • Cost: a 200-step success and a 10-step success are not the same product
  • Debugging: you cannot fix what you cannot localize

Rule of thumb: outcome eval for reporting, trajectory eval for engineering.

The Lucky-Wrong-Path Problem

An agent asked to fix a bug:

  1. Reads the wrong file
  2. Misdiagnoses the cause
  3. Edits a test instead of the source
  4. Tests pass — because the test was weakened
  • Outcome eval: PASS
  • Any human reviewing the trace: FAIL

These “false successes” are the most dangerous eval result: they inflate your metrics and teach you the wrong lessons about your agent.

Every outcome-only score is an upper bound on true quality. The gap is the lucky-wrong-path rate.

Outcome Evaluation Methods

  1. Verifiable checks (gold standard when available)
    • Unit tests, type checks, exact match, database state diff
    • SWE-bench: the patch must make failing tests pass without breaking others
  2. LLM-as-judge on the final answer
    • Reuse the Class 2 judge harness; rubric scores correctness/completeness
    • Works for open-ended tasks (research summaries, plans)
  3. Human grading
    • Expensive; reserve for calibration and high-stakes tasks

Prefer verifiable checks whenever the task admits them. A judge is a proxy; a test is ground truth.

Trajectory Evaluation: What to Score

For each step in the trace:

  • Tool selection: right tool for this subtask?
  • Tool arguments: well-formed, grounded in evidence, not hallucinated?
  • Information use: did the agent use what the tool returned, or ignore it?
  • Ordering: exploration before edits, tests after changes?
  • Recovery: after an error, did it adapt or repeat the same call?

And across the whole trace:

  • Progress: does each step reduce distance to the goal?
  • Termination: stopped when done — not early, not looping

A trajectory rubric is a checklist of failure modes you have actually seen.

Step-Level Judging and Process Rewards

Two families:

  • Process Reward Models (PRMs): a model scores each reasoning step; used heavily in math/reasoning RL
  • LLM judge over the trace: feed the full trajectory (or a compressed view) to a strong model with a rubric

Practical issues:

  • Full traces are long — judges need trace compression or per-step windows
  • Judges inherit the same biases as output-level judges (verbosity, sycophancy)
  • Judging a trajectory costs more than producing one sometimes

Meta-eval applies here too: hand-label a small set of traces, measure judge–human agreement before trusting the judge at scale.

Reference-Based vs Reference-Free Trajectories

  • Reference-based: compare against a gold trajectory (canonical tool sequence)
    • Precise, but penalizes valid alternative paths — agents rarely match the reference exactly
  • Reference-free: judge the trace on its own merits against a rubric
    • Flexible, but noisier and judge-dependent

Middle path used in practice:

  • Score milestones, not steps: did it find the right file? reproduce the bug? run the tests?
  • Milestones are path-independent but still trajectory-aware

Don’t grade the footsteps; grade whether it passed through the checkpoints.

Efficiency as a First-Class Metric

Two agents, same success rate. One uses 10 steps and 40k tokens; the other 200 steps and 2M tokens.

They are not the same agent.

Track per run:

  • Steps / tool calls to solution
  • Input + output tokens (and $ cost)
  • Wall-clock latency
  • Tokens-per-success and cost-adjusted success: the numbers a product team actually budgets against

Success rate is a research metric. Success rate at a cost is an engineering metric.

Reliability: pass@k and pass^k

A single run proves almost nothing about a stochastic agent.

  • pass@k: probability that at least one of \(k\) independent runs succeeds
    • The right metric when you can try many times and keep the best (code with tests)
  • pass^k (τ-bench): probability that all \(k\) runs succeed
    • The right metric when the agent faces real users and must work every time

\[pass@k = 1 - (1-p)^k \qquad pass^k = p^k\]

pass@k rises with retries; pass^k collapses. A demo is a pass@1 sample of size one.

Report variance across seeds, not the best run. An agent that works “sometimes” is a property of \(p\), not of your luck.

Agent Benchmarks: The Landscape

Benchmark Domain What it measures Scoring
SWE-bench (Verified/Lite) GitHub issue fixing Real repo patches Tests pass/fail
GAIA General assistant tasks Multi-step tool use, web, files Exact match
τ-bench Tool-agent-user dialogues Policy adherence under conversation pass^k on env state
AgentBench 8 environments (OS, web, DB, …) Broad agent capability Task-specific
WebArena / OSWorld Web / full OS control GUI action sequences, task completion Env state checks

No benchmark measures “agenticness”. Each measures success in one environment, with one action space, under one scoring rule.

SWE-bench

  • Real GitHub issues from popular Python repos; the agent must produce a patch
  • Scored by running the repo’s test suite: FAIL_TO_PASS tests flip, PASS_TO_PASS stay green
  • SWE-bench Verified: 500 human-validated, non-broken tasks (OpenAI, 2024)
  • SWE-bench Lite: 300-task cheaper subset for iteration

Why it became the standard:

  • Verifiable scoring — no judge needed
  • Long-horizon: real repos, real context management, real tool use
  • Directly matches the coding-agent spine of this course

Caveats: solutions leak into pretraining data; top systems tune scaffolds to the benchmark; resolved-rate gains increasingly reflect scaffolding, not reasoning.

GAIA and τ-bench

GAIA (Meta/HF, 2023): 466 assistant tasks with short verifiable answers

  • Requires web browsing, file handling, code execution, multimodality
  • “Easy for humans, hard for agents” — humans ~92%, early GPT-4 agents ~15%
  • Level 1/2/3 by number of steps and tools needed

τ-bench (Sierra, 2024): tool-agent-user conversation in retail/airline domains

  • A simulated user (LLM) converses with the agent; scored on final database state + policy adherence
  • Introduced pass^k to measure consistency — SOTA agents then scored below 50% at pass^8
  • Exposed that benchmark success and production reliability are different quantities

GAIA measures capability breadth; τ-bench measures reliability under interaction. You need both kinds of number.

WebArena, OSWorld, AgentBench

WebArena: self-hosted realistic websites (shopping, forums, GitLab, maps)

  • Task success checked against environment state, not textual answers
  • Hard: SOTA success rates stayed below ~60% long after text benchmarks saturated

OSWorld: full desktop control (Ubuntu, real apps) — the computer-use benchmark

AgentBench: 8 diverse environments (OS shell, database, web shopping, card games…), a capability profile rather than a single score

Environment-state scoring is the common thread: as agents act in the world, evals must check the world, not the transcript.

Reading Benchmark Numbers Responsibly

Before trusting any leaderboard number, ask:

  1. Contamination: were the tasks (or their solutions) in pretraining data?
  2. Scaffold vs model: how much of the gain is the harness, retries, and prompt engineering around the model?
  3. Saturation: is headroom left, or is everyone at 90%+ arguing about noise?
  4. Cost: what did each solved task cost in tokens and wall-clock?
  5. Selection: was the benchmark chosen because the system does well on it?

A benchmark is a proxy for a distribution of real tasks. Proxies get gamed — Goodhart applies to agents with extra force.

Failure Taxonomies

The deliverable of an eval campaign is not the score — it is the failure analysis.

A working taxonomy for coding-agent failures (from the course spine, Class 8):

  • Wrong localization — edited the wrong file / wrong function
  • Test-gaming regression — made tests pass by weakening them
  • Infinite loop — repeated identical failing tool calls
  • Context overflow — lost the task during compaction
  • Hallucinated API — called functions/flags that don’t exist
  • Premature stop — declared done with subtasks open
  • Sandbox/policy violation — attempted disallowed actions

Taxonomy categories should come from your traces, not from this slide. This list is a starting point, not a constant.

Observability: Traces Are the Raw Material

You cannot evaluate what you did not record.

  • Trace: one full agent run — every LLM call, tool call, observation, decision
  • Span: a unit inside the trace (one tool call, one retry, one sub-agent run)
  • Log inputs, outputs, token counts, latency, cost, and environment diffs per span

Tooling (all span-based, all have free tiers):

  • Langfuse — open source, self-hostable
  • Weave (W&B), LangSmith (LangChain) — hosted, framework-adjacent

Tracing is not a production luxury. It is the dataset your evals run on.

Offline vs Online Eval for Agents

Offline (before deployment):

  • Benchmark suites (SWE-bench slice, GAIA subset, your own task set)
  • Regression suite built from past failures — every production failure becomes a test case
  • Run per change: model swap, prompt edit, tool change

Online (in production):

  • Sampled trace review (judge or human) on live traffic
  • User signals: task abandonment, retries, corrections, thumbs
  • Guardrail metrics: policy violations, budget overruns, loop detection

Same three-regime structure as output eval (offline / online / guardrails) — but the unit is now a trace, not a response.

Eval-Driven Agent Development

The loop that actually improves agents:

  1. Run the agent on a task set; record full traces
  2. Failure analysis: label failures into your taxonomy
  3. Turn top failure categories into regression evals
  4. Fix the agent (prompt, tool, scaffold)
  5. Re-run; confirm the fix; check for regressions elsewhere
  6. Repeat
  • Resist prompt-tweaking against vibes; every change is validated against the suite
  • The eval suite is the product spec for agent behavior

Eval-driven development: you don’t have an agent quality problem, you have a measurement pipeline that produces fixes.

Modality Changes the Eval

The action space defines the metrics:

  • Text agents (this course): trajectory quality, task success, tokens-per-success
  • Voice agents: latency as a first-class metric (time-to-first-token, interruption handling), WER of the ASR leg, user satisfaction over time within one call
  • Computer-use agents: action correctness (right click, right element), recovery from failed clicks, completion on GUI benchmarks (WebArena, VisualWebArena, OSWorld)

Eval methodology is not portable across modalities. When you get to voice or computer use, expect to rebuild the rubric around the new action space.

Open Problems

  • Long-horizon eval: tasks spanning hours/days; how do you grade a 10,000-step trace?
  • Judging the judges of trajectories: meta-eval for step-level judges is nearly unsolved
  • Eval cost: a full agent eval run can cost more than a day of production traffic
  • Self-generated evals: agents writing their own regression tests — promising and circular
  • Security evals: prompt injection, tool abuse, sandbox escapes need adversarial benchmarks, not just accuracy benchmarks

Takeaways

  1. Agents produce paths, not answers — evaluate the path
  2. Outcome eval for reporting; trajectory eval for engineering
  3. Milestones over footsteps; verifiable checks over judges
  4. Report pass^k and cost-per-success, not one lucky run
  5. The failure taxonomy — built from your traces — is the real deliverable
  6. Tracing is eval infrastructure, not observability garnish

You can’t improve what you can’t measure — and for agents, measuring means recording.
